## 2. Voice — The Two-Layer Model

Dopemux has **two distinct voice registers**. Every surface picks one.

### 2A. Operator-Production Register (default, load-bearing)

Authority: [`BRAND_SYSTEM.md`](../BRAND_SYSTEM.md) + [`VOICE_GATES.yaml`](../dopemux_voice_branding_bundle/VOICE_GATES.yaml) + [`scripts/brand_lint.py`](../scripts/brand_lint.py)

**Use for**: CLI output, logs, dashboards, HTTP error messages, TUI, any surface a non-dev user might read.

**Core rules**:
- Operator-first: write for the person doing the work, not spectating.
- Terse, procedural — lead with the result, then minimum context to act.
- Calm, specific, unsentimental. **No hype, no mascot, no visionary framing.**
- Receipts over vibes: every non-trivial claim is evidence-backed.
- If state can't be proven, label it `unknown`. Don't invent.
- End with a `NEXT:` action.

**Output shape**:
- One-line success by default.
- Multi-line only when listing state, blockers, or next steps.
- Consistent labels when structure helps: `Status:`, `Reason:`, `Next:`.
- Deterministic ordering in lists and tables.

**Error shape** (REQUIRED in production UI — enforced by `brand_lint.py`):
- Use `error_panel(problem, why, fix)` — 3-part structure with `[BLOCKER]` chip.
- Include the failing surface (command/path/service/port/endpoint/file).
- Include the missing prerequisite when known.
- Separate observed failure from inferred cause.

**Examples**:
- ✅ `Failed: task-orchestrator health check returned 503.`
- ✅ `Blocked: missing workspace id.`
- ✅ `Warning: ConPort reachable, but decision history query timed out.`
- ✅ `Started: MCP services for current workspace.`
- ✅ `Unknown: dashboard state could not be verified.`
- ❌ `Your workflow is now supercharged.`
- ❌ `Something went wrong. Please try again.`
- ❌ `All set! You're good to go.`

### 2B. Brand-Identity Register (personality, gated)

Authority: [`BRAND_VOICE_BIBLE.md`](../dopemux_voice_branding_bundle/BRAND_VOICE_BIBLE.md) + [`SPECIMEN_LEDGER_ENRICHED.csv`](../dopemux_voice_branding_bundle/SPECIMEN_LEDGER_ENRICHED.csv) (184 curated specimens)

**Use for**: brand docs, marketing, internal system prompts, voice-gated CLI banners, session-start headers, developer-facing roast surfaces. **Never** in HTTP exceptions, form validation messages, or any surface that might reach a non-developer user.

**Six voice modes** — context-activated, not user-chosen:

| Mode | Trigger | Tone |
|---|---|---|
| `FilthDaemon` | Drift, untagged, sanitization events | Consequence + imperative |
| `ClinicalForensics` | Privacy, provenance, determinism | `FACT`/`INFERENCE` split, thresholds, `UNKNOWN + TODO` |
| `UXScold` | Vague input, stuck operator (dev surfaces only) | Roast + one step + evidence request |
| `UIStrict` | Microcopy, form fields | `{label, message, action}` — no threats, no metaphors |
| `BannerOneLiner` | Session start, headers | 1–2 punch lines, then utility |
| `KinkAccent` | Optional spice layer | Consent-coded humor only; never load-bearing |

**Mode routing** (lint-enforced):
- `UX_SCOLD` and `FILTH_DAEMON` tokens are **forbidden in operational UI Python files** ([`brand_lint.py:117`](../scripts/brand_lint.py)). They're for brand docs, CLI banner contexts, and agent prompts — not live UI.
- `UIStrict` is the only mode with no prohibited placements.

### 2C. Surface Guidance (bounded, advisory unless enforced)

These are preferred output shapes for common surfaces. They do not override the runtime gates in §§3, 6, and 7.

#### CLI surface
- Terminal-native, procedural, and terse.
- Zero to two banner lines maximum before utility.
- One-line success by default; multi-line only for state, blockers, or next steps.
- Corrective wit is allowed only when it clarifies the problem instead of obscuring it.

Preferred pattern:
```text
STATUS: [CHIP] condition
KEY FACTS:
- observed fact
- observed fact
RISKS / DRIFT:
- risk if any
NEXT: exact action
```

#### UI surface
- Crisp, direct, and minimal.
- Avoid shame, consequence theater, or mascot-style banter.
- Prefer `{label, message, action}` structure for actionable UI strings.
- Prefer `required` / `missing` over insulting or playful failure phrasing.

#### Agent surface
- Use a clinical-forensics contract for non-trivial analysis.
- Label direct observations as `FACT`.
- Label derivations as `INFERENCE`.
- When state cannot be proven, use `UNKNOWN + TODO` instead of guessing.

Preferred pattern:
```text
FACT:
- observed fact
INFERENCE:
- derived conclusion
RISKS / DRIFT:
- explicit uncertainty
NEXT: exact action
```

#### Guardian / focus-protective surface
- Use calm, non-sentimental reminders.
- Prefer deterministic wording for time-based alerts and interruption prompts.
- End with one clean next step instead of stacked guidance.

## 3. Hard Rules (Lint-Enforced)

### 3.1 Forbidden phrases (hard_avoid — blocks output)
From [`VOICE_GATES.yaml:5`](../dopemux_voice_branding_bundle/VOICE_GATES.yaml):
- "as an ai"
- "probably"
- "maybe"
- "generally speaking"

### 3.2 Discouraged phrases (soft_avoid — warning)
- "no worries"
- "it's okay"
- "don't worry"
- "hope you're doing well"

### 3.3 Shame-phrase prohibition (operational UI only)
From [`brand_lint.py:111`](../scripts/brand_lint.py): the phrases **"public shame"**, **"roast escalation"**, **"shame you"** and the tokens `VoiceMode.UX_SCOLD` / `VoiceMode.FILTH_DAEMON` are prohibited in 10 operational UI Python files.

### 3.4 Forbidden terminology (naming)
Never use these as feature/product names:
- `magic`, `brain` (as feature), `autonomous`, `smart`, `seamless`, `next-gen`

Prefer: `operator`, `workspace`, `run`, `task`, `service`, `route`, `health`, `context`.

### 3.5 Required closers (every agent/CLI output)
Must end with one of: `NEXT:`, `Next:`, `Receipt:`, `PROGRESS`.

### 3.6 Structure gates (non-trivial claims)
- `FACT` / `INFERENCE` labeled split required.
- `UNKNOWN + TODO` required instead of guessing.

### 3.7 Preferred message patterns

These patterns are safe defaults when no more specific surface contract exists.

**Success**
- State what succeeded.
- Add the minimal evidence or changed state.
- End with `NEXT:` only if an operator action is still required.

**Warning / degraded**
- State what is degraded.
- State impact.
- State the next mitigating action.

**Failure**
- State the failing surface first.
- Separate the observed failure from the inferred cause.
- Give one concrete next action.

## 5. Component Standards (CLI/TUI)

### Every command MUST
1. Import `from dopemux.console import console` (never raw `Console()`).
2. Show a status chip on completion.
3. Use themed style names, never raw color strings.
4. Show duration for operations > 1 second.

### Error messages MUST
1. Use `error_panel(problem, why, fix)` or wrap in `styled_panel(border_style="error")`.
2. Use 3-part Problem / Why / Fix structure.
3. Include an actionable step.
4. Use `[BLOCKER]` chip.

### Tables MUST
- Box: `box.ROUNDED` (default); `box.SIMPLE` for compact inline.
- Zebra stripe if > 3 rows.
- Right-align numbers; left-align text; center-align status.
- Title: nerd-font glyph + space + title text.

### Progress MUST
- Spinner: `dots12` for all operations.
- Bar: complete `#7DFBF6`, remaining `#1A0520`, pulse `#FF8BD1`.
- Show time remaining if > 5 seconds.

### Layout rules
- Max width: `min(terminal_width, 120)`.
- One blank line before/after panels.
- Section breaks via `console.rule(style="rule.line")` only — never manual box chars.
- Progressive disclosure: default summary → `--verbose` → `--debug`.

### Render modes (via `DOPEMUX_RENDER_MODE` or `NO_COLOR`)
- `RICH` (default) · `PLAIN` · `COMPACT` · `AUDIT`

### ADHD-oriented copy preferences

When writing for focus-sensitive operator flows, prefer:
- deterministic reminder wording over novelty phrasing
- one required closer instead of multiple competing next steps
- explicit `unknown` / `missing` language over soft reassurance
- stable chip usage so urgency can be skimmed before full reading
