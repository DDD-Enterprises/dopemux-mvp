    2. **Ports #928's ledger hardening** into the restored gate (not #928's

       gate file — no gate duplication):
    - **Incompatible-ledger fail-closed** — `verify` introspects the
    ledger's
         columns; if they aren't a superset of the native
    `{version, filename, checksum_sha256, success}` schema, or if inspection
         raises an unexpected DB error, the gate returns a structured
         `migration ledger validation failed` result instead of leaking a
         column-level SQL traceback.
    - **No-mutate guard** — `apply` refuses to mutate a pre-existing foreign
         ledger: `legacy migration ledger cannot be mutated by this gate`.
       - **connect() driver-error wrap** — `psycopg2` errors fail closed as
    `database connection failed` (a pre-existing traceback gap surfaced by
    the
         in-container smoke test; same safety class as #928).
    3. **Adds the ADR**
    `docs/90-adr/adr-conport-migration-foundation-gate.md`
    (absent from `main`), documenting the gate, the clobber+restore, and the
    port.

    **Output-contract note:** #917's `{"status":"pass"|"fail-closed"}`
    envelope and
    exit `0`/`2` are preserved. #928's
    `applied_verified`/`verified`/`failed` status
    strings and exit `1` were deliberately **not** adopted (they would break
    #917's
    merged contract + tests). The hardening's error *messages* are ported
    verbatim;
    the *envelope* stays #917's. "legacy" in the no-mutate message is #928's

    for "a pre-existing ledger this gate does not own."
