## Findings

**F-1 · MEDIUM · allowlist escape in working tree (packet stop condition, source-clean).**
`.claude/claude_config.json` is modified with a worktree-local MCP instance rewrite (`DOPEMUX_INSTANCE_ID` / `DOPEMUX_WORKSPACE_ID` → this worktree path), and `.claude/.untracked-work-probe-cache.json` is untracked. Neither is in Scope IN. Both look tool-generated (`dopemux mcp init` / hook cache), not authored. If the commit is made with `git commit -a` or `git add -A`, machine-local paths land in the trust-root PR. Restore `.claude/claude_config.json` to `HEAD` and stage only allowlisted paths.

**F-2 · MEDIUM (pre-existing, amplified) · "trusted main ref" is a docstring claim, not enforced in code.**
`solo_owner_security_release.py:3-4` and the ADR assert the roster comes from "the trusted main ref", but `classifier.py:112` resolves it as `Path(__file__).with_name("known_reviewers.json")` and `intake.py:60-65` calls `build_artifacts` without `known_reviewers_path` — so the roster is read from whatever checkout the steward runs in. This predates the diff (PR #1131), but the MEMBER widening makes it more load-bearing: the roster is now the *only* gate separating "the sole maintainer" from "any organization member." Chain: an org MEMBER opens a PR rewriting `known_reviewers.json` to `["attacker"]`; if the steward runs against PR-branch content, `solo_owner_roster_eligible` becomes true for them and the solo phrase could clear the red lane that protects the roster itself. Residual barriers (all still intact): the roster path is red-lane classified with rename coverage (`classifier.py:250-262`), embedded audit must be `PASS`/`PASS_WITH_RISKS`, proof must bind the exact head, all required CI green, plus branch protection/CODEOWNERS outside this tool. Not introduced here and not a blocker for this packet, but it should become its own packet: resolve `known_reviewers.json` from `origin/main` (e.g. `git show origin/main:tools/pr_steward/known_reviewers.json`) rather than the working tree.

**F-3 · LOW · no code-level bot rejection on the solo-human path.**
`solo_owner_roster_eligible` compares logins only; nothing rejects a `*[bot]` login, and `classifier.py:1357` shows the codebase already has `_normalize_bot_login` for exactly this shape. Item 7 passes today purely because `trusted_security_release_approvers` is `["hu3mann"]`. A one-line fail-closed guard (reject operator logins matching `[bot]` / app suffixes in the solo path) would make the invariant code-enforced instead of config-enforced, and cost nothing.

**F-4 · LOW · test-coverage gaps in the new suites.**
No direct case for `HARVEST_INCOMPLETE` (behavior is correct by the generic non-`SECURITY_RELEASE_` prefix rule at `:194`, and sibling blockers are tested, so this is coverage not correctness), and no bot-login rejection case. Also untested: PR assoc `MEMBER` + comment association *absent* → activates with `operator_association == "MEMBER"` (`:302`). That is intended behavior inherited from the OWNER-only implementation, but it is the one path where authority rests on a single field, and it deserves a pinning test.

**F-5 · NIT · ADR frontmatter dates moved backwards.**
`last_review` / `next_review` changed `2026-07-27` → `2026-07-26` (and `-10-25` → `-10-24`) while `date: '2026-07-27'` was left in place, so `last_review` now precedes the document date. Given this repo runs frontmatter hygiene gates, align the three fields.

## Remaining risks

1. **`MEMBER` is a weaker GitHub claim than `OWNER`** — it means "member of the owning organization," not repo admin. The policy is only as strong as the single-entry roster; F-2 is therefore the real trust-root question, not the association set itself. The choice is sound and correctly documented in the ADR at `:130-153`, but it shifts weight onto a file whose sourcing is unverified in code.
2. **Missing-association tolerance survives the change.** If a harvest omits `authorAssociation` on issue comments, activation rests solely on the PR-level association (and vice versa). Fail-closed only when *both* are missing (`:284-289`). Unchanged from #1131; correct per ADR, worth an explicit test (F-4).
3. **Newest-candidate selection sorts on timestamp strings** (`:180`) and comments with no timestamp sort to `""`, i.e. oldest. Harmless here because every candidate already matched the exact PR number, exact head, and operator login, so all candidates are equivalent authorizations. No action needed.
4. **No runtime/live evidence in this audit.** Verdicts are code-inspection plus unit/integration tests. End-to-end behavior against real GitHub `authorAssociation` values for the org case (`DDD-Enterprises/dopemux-mvp` + `hu3mann` = `MEMBER`) is asserted by fixture, not observed. The org-app path (#1133) is untouched and remains the stronger route where an app installation exists.
