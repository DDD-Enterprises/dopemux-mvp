# System Inventory

**Claude Code (Anthropic)** – A developer-centered AI coding assistant running on Anthropic’s Claude models. It provides a CLI, IDE and browser interface. Internally it is a multi-agent system: a “lead” Claude agent can spawn subagents (“Explore”, “Plan”, general, or custom) in parallel, each with specialized prompts and tool access【19†L19-L28】【69†L282-L284】. Execution is a synchronous conversation loop, with the lead agent delegating tasks and merging results. Routing among agents is manual (you explicitly invoke subagents or agent teams via commands). Tools are tightly integrated (file I/O, terminals, searches, Git, etc.) and an open **MCP** protocol lets Claude Code query external data sources (GitHub, Slack, databases)【69†L261-L269】【58†L38-L46】. Memory is twofold: the current context window plus persistent “auto memory” (it writes learnings like build commands and debugging tips to CLAUDE.md between sessions)【69†L270-L274】. Strengths: rich dev integration (VS Code, CI, CLI), multi-agent parallelism, and deep codebase awareness (via MCP). Limitations: constrained by Claude model context lengths and latency; subagents do not spawn other subagents; orchestration is user-driven, so complex flows need manual setup (e.g. planning vs execution phases).

**OpenAI Codex (CLI/Agents)** – An autonomous coding assistant (successor to Copilot CLI) built on GPT models. It offers CLI/IDE interfaces where the LLM can spawn **subagents** by user commands. Codex’s architecture is agent-centric: each subagent is a separate GPT instance with its own system prompt, permissions and tools【19†L19-L28】. Execution is interactive and largely synchronous, although it supports explicit background tasks (you can “/background” a task). Routing is explicit: you invoke agents by name (e.g. `/agent researcher`) or the system may suggest spawning agents. Tools include OS commands, web search, documentation retrieval (via **MCP/”skills”**), and coding tools; Codex SDK supports plugins and policies. Memory comes from conversation history and optional Pinecone/JSON store, but is application-managed. Strengths: built-in support for branching “subagent workflows” and tool plugins, plus sandbox approvals. Weaknesses: still nascent – agents must be explicitly invoked (no autonomous planning by default), and open-source AutoGPT-style loops reveal instability (hangs, hallucinations)【51†L127-L131】. Debugging complex tasks is hard due to opaque LLM reasoning.

**Cursor (Acme Labs)** – A desktop IDE agent with a multi-agent, parallel architecture. Cursor 2.0 can run *up to eight* independent AI agents simultaneously【32†L148-L156】. Each agent gets its own isolated workspace (via Git worktrees or remote VMs) and role (e.g. *Architect*, *Planner*, *Implementation*, *QA*). Under the hood, Cursor ships a proprietary “Composer” LLM (fast MoE + RL-trained model) and also leverages external models (Claude, GPT-4o, etc.)【30†L247-L254】【32†L119-L127】. Execution is largely asynchronous: agents work in parallel on subtasks, and a human “project lead” reviews and merges their outputs. Routing is human-guided: you assign tasks or workflows to agents; the system also runs ensemble experiments (e.g. running the same task on multiple models concurrently) to pick the best result【30†L232-L241】. Tool integration includes full IDE features: multi-file editing, a sandbox terminal, automated tests, DOM/browser tools, and Slack/Voice interactions【30†L247-L254】【32†L148-L156】. Cursor’s memory is mostly the codebase itself and version control – it does not use a separate long-term memory store. Strengths: extreme parallelism (multi-model A/B testing), built-in testing and code review flows, low-latency model (250 tokens/sec)【32†L119-L127】【32†L148-L156】. Limitations: heavy resource usage (8 agents + VMs), and costs; still requires human oversight (developers review PRs). Emergent agent interactions can be complex to manage.

**Replit Ghostwriter (and Agents)** – Replit’s AI coding assistant. Ghostwriter is a multi-feature **multi-model** system rather than a multi-agent one. It uses specialized models for different tasks: a distilled CodeGen model for live code completions (400 ms latency)【36†L169-L178】, a finetuned CodeBERT for semantic code search【38†L337-L345】, and large models (OpenAI) for “Explain Code”, full file generation or refactoring【38†L363-L372】. The system is integrated into Replit’s IDE/Editor, handling streaming completions with AST-aware post-processing and heuristic filtering【36†L237-L246】【36†L299-L307】. There is no persistent agent state or memory beyond the open file context (though Replit’s “DeepWiki” and workspace embeddings can provide document retrieval). Strengths: very low-latency, rich editor UX (whitespace matching, streaming, context-aware suggestions)【36†L172-L181】【36†L313-L322】; specialized search and explain features. Limitations: one-shot assistance (no multi-turn planning), context limited to current files, and no built-in orchestration or learning over sessions.

**Devin (Cognition)** – A SaaS “AI software engineer.” Devin’s architecture is cloud-based: each “Devin session” runs on an isolated VM with its own IDE and tools (terminals, compilers, test runners). Devin supports *managed sessions*: a “coordinator” session can orchestrate multiple child Devin sessions in parallel, each on its own VM【42†L153-L162】. The coordinator breaks down tasks, spawns child sessions (with specific prompts or “playbooks”), and later merges their PRs【42†L155-L164】. Execution is asynchronous and event-driven: child Devins run autonomously until complete or paused. Tool integration is deep: Devin can run commands, tests, and even write its own scripts (so it “decreases mouse clicks” over time)【40†L124-L132】. It also includes a knowledge base (DeepWiki) for repository facts and automatically updated “wikis” of the codebase【45†L86-L95】. Memory spans short-term (conversation context) and long-term (playbooks, indexed repo content). Strengths: enterprise-grade parallelism and learning (fine-tuned on company data), built-in version control (every session is a branch/PR), and knowledge management. Limitations: high complexity/cost (multiple VMs per user), reliance on fine-tuning, and potential synchronization conflicts which Devin’s coordinator must resolve.

**LangChain / LangGraph (Open Source)** – A developer framework for building agentic LLM workflows, rather than a single product. LangChain lets you script LLM “agents” with arbitrary tool integration (retrieval, APIs) and optional memory modules. LangGraph (part of LangChain) is an orchestration library that represents agent flows as graphs with state. Architecture is code-driven: you define “steps” and “edges” for how agents call LLMs and tools. Execution can be synchronous or async per your code. Routing is user-defined: you build the control logic (branch, loop, parallel) explicitly in your graph or agent. Tool integration is extremely broad (search, Python REPL, web requests, custom APIs). LangGraph provides built-in memory: short-term state is checkpointed to a database per “thread” so conversations can resume【49†L90-L99】, and long-term stores (vector DBs or SQL) can be used for facts【49†L146-L154】. Strengths: high flexibility and transparency (open-source, customizable); you can add human-in-loop steps easily. Limitations: no out-of-box agent – you must implement coordination logic yourself; can add significant overhead/complexity if not structured well.

**AutoGPT / CrewAI** – Two leading multi-agent frameworks. *AutoGPT* (Open-source) embodies a single fully autonomous agent with a goal loop: it recursively plans and uses tools. It has broad LLM dependency (GPT-4, etc), memory (vector/Pinecone), and plugin tools. In practice, AutoGPT often “unwraps” as a local Python program that iteratively calls the LLM and executes tool commands. Execution is asynchronous/open-ended (it continues until goal met or manual stop). Routing is implicit: the agent decides what to do next. In contrast, *CrewAI* is a commercial multi-agent orchestration platform. CreWAI has a “crew” of role-based agents (e.g. Researcher, Analyst, Writer) defined by the user. The platform provides a visual editor and API to assemble sequential or parallel workflows【51†L98-L107】. CrewAI handles execution with containerized agents and provides built-in workflow tracing and guardrails【52†L129-L137】. Both support tool use (via LangChain under the hood); CrewAI emphasizes reliability (role assignments, monitoring, optional human review) while AutoGPT emphasizes autonomy. In summary: AutoGPT’s model is one LLM planning loop, CrewAI’s model is a structured pipeline of agents. Strengths: *AutoGPT* can demonstrate agentic behavior with minimal setup, *CrewAI* is designed for production with monitoring and role separation. Weaknesses: *AutoGPT* is prone to getting stuck in loops or hallucinations【51†L127-L131】, whereas *CrewAI* requires upfront workflow design and is currently a closed platform. (See limitations below.)

**Vercel AI SDK** – A TypeScript/Node library (npm package) for building AI-powered web apps (Next.js, Svelte, etc). It is **not** a multi-agent system – rather, it abstracts LLM calls. At its core is a unified API (`generateText`, `generateObject`, etc) that can call any LLM provider (OpenAI, Claude, etc) by simple model spec【55†L1725-L1733】. It supports streaming and structured output (type-safe JSON via Zod schemas)【56†L1760-L1770】. Execution is synchronous (awaiting LLM responses) and orchestrated by the developer’s code. The SDK includes optional tool calling: you can register a JavaScript function as a “tool”, and the LLM output is constrained to call it【56†L1779-L1788】. It has no built-in agent or memory model beyond what you implement. Strengths: unifies multi-provider integration, rich type-checking and streaming UI primitives. Limitations: purely a developer toolkit – you still write the orchestration logic. No built-in agent behavior, state, or multi-agent abstractions.

**LiteLLM (Model Routing)** – An open-source LLM proxy/router (written in Python). Its architecture is that of a resilient gateway: it load-balances requests across multiple model deployments or providers, with priority queues, timeouts, cooldowns and fallbacks【17†L49-L58】. Execution is synchronous per request. Routing strategy is rules-based: e.g. you can route all requests for model “gpt-5” to a given deployment; the proxy handles retries and failover. It offers no agent model or memory – it simply forwards LLM API calls. Tool integration: none (it is agnostic, just proxies). Strengths: ensures reliability at scale (automatic retries, fallback when one provider fails, per-model priority)【17†L49-L58】. Limitations: overhead of another hop and Redis dependency; not directly relevant to multi-agent logic.

**MCP-based Tools (Model Context Protocol)** – MCP is an open standard (by Anthropic/OpenAI) for connecting AI agents to external data. Systems that use MCP (e.g. Claude Code, ChatGPT apps) typically have **MCP servers** that expose data sources (GitHub, Slack, databases) and **MCP clients** (agent apps) that query them. Architecture: MCP defines APIs over HTTP. An agent includes calls to MCP endpoints to fetch relevant info (documents, search results, tool outputs) which get inserted into the prompt. Execution: synchronous API calls during prompting. Routing: requests go to appropriate MCP server (e.g. `get-google-drive-files`). Memory: persistent in the data sources, not in the model. Example signals: Anthropic’s docs mention pre-built MCP connectors for Slack, GitHub, Postgres【58†L51-L60】. Strengths: scalable, standardizes tool integration, let agents “call out” to systems. Limitation: still emerging in ecosystems; requires running MCP servers and designing them to be secure.

**Tmux-Based Dev Workflows (Community)** – Ad-hoc orchestration using terminal multiplexers (tmux) to run multiple CLI agents concurrently. In these setups (often with Gemini CLI or Claude CLI), each tmux pane runs an independent agent process. One pane acts as “system orchestrator” (instructions and handoffs), others as worker agents (frontend dev, backend dev, etc)【60†L145-L154】. Communication is by copying text between panes or via shared files. Execution is parallel but clunky: status must be monitored manually. This pattern emerged in hacky prototypes: e.g. one user built a “conductor” script (on GitHub) to spawn tmux agents and report their states【61†L188-L196】. Memory is simply the code repo and files (Git is used as the state log)【60†L165-L174】. Strengths: simple to set up with existing CLI tools. Limitations: very ad-hoc – no visualization, no automated orchestration (scales poorly beyond a few panes)【61†L169-L178】.

**CI/CD Pipelines (GitHub Actions, Buildkite, etc.)** – Mature automation tools often repurposed for orchestrating AI tasks. These are event-driven, YAML-defined workflows: jobs run on runners (VMs/containers) triggered by events (e.g. PRs). They support parallel/conditional steps and integrate with code repos. Memory is limited to artifacts and workspace caches. While not specifically AI-focused, they exemplify reliable orchestration patterns: explicit sequences of steps, parallel matrix jobs, and integration with external tools/APIs. Strengths: robust, well-understood, with retries and auditing. Limitations: static pipelines not self-adjusting; new ML tasks require custom actions or scripts.

# Recurring Patterns

- **Supervisor/Coordinator Agents:** Many systems use a primary agent or human-in-loop to oversee others. For example, Claude Code’s lead agent assigns tasks and merges subagent outputs【69†L282-L284】. Devin’s “coordinator” session scopes work, spawns child sessions in parallel, monitors ACU usage, and compiles results【42†L155-L164】. Community workflows often use one pane as “System Orchestrator” that routes tasks to worker agents【60†L145-L154】. This central control prevents uncontrolled branching.

- **Agent Roles & Pipelines:** A common model is *divide-and-conquer*: define specialized roles (planner, implementer, reviewer) and hand off tasks between them. Cursor names agents like *Architect*, *Frontend*, *QA* with clear responsibilities【60†L145-L154】. CrewAI similarly has role definitions (Researcher, Analyst, Writer) in a sequential/parallel pipeline【51†L98-L107】. In the example support-agent flow【65†L730-L739】【65†L748-L754】, tasks flow through triage, retrieve, plan, check, execute, verify, then escalate. Decomposition is often done by an LLM (a “planner” subagent) or predefined playbook.

- **Task Decomposition:** Systems either rely on LLM planning or pre-structured decomposition. In Claude Code, you might prompt the agent (or it might automatically) break a feature request into steps (using a “Plan” subagent). Cursor’s *Planner* agent writes detailed execution plans. Devin uses “playbooks” (templates of steps). CrewAI requires you to explicitly break the goal into sub-tasks for each agent. Some autoprompt tools (AutoGPT, LangChain chains) use the LLM itself to recursively split tasks.

- **Audit and Verification:** Almost every system incorporates checks. For coding, automated tests are key (Cursor generates and runs tests on its changes). Claude Code examples highlight verifying fixes in context. The Hatchworks guide emphasizes a “VERIFY” step to confirm side-effects【65†L748-L754】. Human review is also standard: e.g. Cursor has the developer accept PRs, and CrewAI advises “human-in-loop” as a feature【68†L96-L104】. Logging outputs and using schemas/patterns for tool calls (idempotency keys, JSON schemas) is another audit strategy【65†L697-L704】.

- **Failure Handling:** Production systems build in retries, timeouts, and fallback modes. LiteLLM, for example, uses timeouts and cool-downs to avoid infinite retries【17†L49-L58】. Agents often have budget controls (limit recursion depth or token usage). If an agent “gets lost,” platforms may escalate. The Hatchworks anti-pattern list warns that without fallbacks, agents will loop or hallucinate【65†L672-L681】. CrewAI advises surfacing failures loudly for quick fixes【68†L101-L109】. In practice, systems detect uncertain outputs (low-confidence or policy triggers) and either retry with a different prompt, revert to a human, or halt.

# What Actually Works

- **Specialized Parallel Agents:** Systems running agents in parallel with clear roles have been successful. Cursor’s 8-agent parallel workflow lets each agent work independently (e.g. one on UI, one on business logic)【32†L148-L156】. Devin’s parallel sessions strategy at Nubank (1000s of similar refactors) showed massive speedups【42†L155-L164】. Controlled parallelism avoids bottleneck.

- **Strict Orchestration:** In practice, every proven system enforces structure. Successful pipelines have explicit stages (plan, execute, test) and centralized oversight. Example: a customer-support agent flow with explicit triage, policy-check, verify and escalation steps【65†L730-L739】【65†L748-L754】. CrewAI/Devin style “crew leads” guide subordinate agents rather than free-for-all.

- **Developer-in-the-Loop:** True production use always includes human checkpoints. Even Cursor, which is highly autonomous, requires the developer to review and merge code. Devin users review PRs. CrewAI’s best practices start with human review as a *feature*【68†L96-L104】. This hybrid approach catches errors and gradually trains trust.

- **Reality Checks (Tests, Linting, Schemas):** Systems that integrate actual execution or validation succeed. Cursor auto-generates and runs tests; many agents use linters or compile-check. Hatchworks notes that all tool calls should be “schema-validated” and idempotent【65†L697-L704】. Teams often write regression tests for agent outputs as if they were developer code.

- **Incremental Complexity:** Products that started simple and added agents/modules gradually are common. CrewAI’s own advice is to begin with “one thing badly” and human oversight【68†L96-L105】. Dev teams often first automate small tasks (e.g. repo-wide regex updates) before full self-serve coding. In reality, systems in production have evolved from smaller, single-agent workflows to multi-agent collaboration as confidence grew.

# What Fails in Practice

- **Uncontrolled Agent Loops:** Fully autonomous agents (like vanilla AutoGPT) frequently loop or wander off-topic. As one review noted, AutoGPT “often gets stuck or loops,” leading to unpredictable behavior【51†L127-L131】. Without tight orchestration, agents can chase their tail or repeatedly call the same tool.

- **Hallucinated Outputs:** All LLM agents hallucinate occasionally, but it’s particularly hazardous when unchecked. In coding contexts, this leads to code that “looks correct” but doesn’t actually work. Agents without verification produce more hallucinations. Reliable systems either use LLM outputs only for suggestions (and validate) or incorporate auditing steps【65†L748-L754】.

- **Routing Chaos:** When multiple models or subagents are available, poor routing causes inefficiency. For example, letting an LLM choose tools indiscriminately (“unbounded autonomy”) is cited as an anti-pattern【65†L672-L681】. In practice, we see cost blow-ups: e.g. running GPT-4 on minor tasks or invoking web search unnecessarily spikes tokens. Systems that do not enforce strict tool permissions or cost budgets quickly overspend.

- **Cost Explosions:** Agents with large context or insufficient stopping criteria run up cost. E.g. a poorly constrained loop in AutoGPT could make thousands of API calls. Even multi-agent setups (8 agents each with large models) cost a lot if not limited. Effective systems enforce budgets and terminate long jobs.

- **State Drift:** Over long sessions, agent context can drift or grow stale. If the agent never resets or ignores new code changes, it loses sync with reality. This “death spiral” is seen when an agent repeats irrelevant ideas without ground truth. Persisting memory and regularly retrieving fresh context (RAG) helps; ignoring that leads to degraded output over time.

# Implementation Signals

- **Isolated Environments:** Many designs use container/VM isolation per agent. Devin’s managed Devins each run in an isolated VM【42†L155-L163】. Cursor’s “background agents” run on separate Ubuntu VMs【32†L165-L172】. Even Gemini CLI examples use Git worktrees to sandbox agent changes【32†L148-L156】. This prevents cross-contamination of context.

- **State Persistence:** Systems store state externally. LangGraph checkpoints conversation state to a database, so threads can resume【49†L90-L99】. Git is often used as the “memory” (agents commit their outputs). Some use vector DBs for long-term memory (LangChain’s stores). Guidelines emphasize making memory writes explicit and governed【65†L601-L610】.

- **Queues and Event Buses:** In robust setups, agent tasks go through queues or event systems. LiteLLM maintains priority queues of LLM requests to enforce rate limits and priorities【17†L49-L58】. CrewAI suggests “workflow tracing” which implies event logs【52†L129-L137】. In DIY setups, simple in-memory queues (e.g. Redis) coordinate tasks; in production, one might use Kafka or cloud pub/sub to signal agent completion or errors.

- **CLI/SDK Orchestration:** Most tools wrap orchestration in CLIs or SDKs. Claude Code’s CLI pipes commands or logs into the agent【69†L288-L297】. Replit/Gemini have their own CLI to spawn agents. Vercel AI SDK provides functions (`generateText`, `tool()`) that simplify coding agents. Notably, many workflows use shell scripts or Makefiles to glue steps (the “Unix philosophy” as Claude Code docs mention【69†L288-L297】).

- **Monitoring and Metrics:** Production systems export traces and metrics. LangSmith (LangChain’s platform) provides step-by-step audit trails. Developers often log each agent action and tool call. Reliable teams record token usage per step, success rates, and have dashboards for agent health (as CrewAI suggests “workflow tracing”【52†L129-L137】).

- **Idempotent Tooling:** As recommended, side-effect tools are wrapped with idempotency keys or dry-run checks【65†L697-L704】. For example, API calls to update tickets are done inside simulated mode first. This makes retries safe and eases debugging.

Overall, these signals – isolated agents, explicit state stores, queued task execution, CLI workflows and careful logging – distinguish production AI orchestrations from quick demos. They ensure reliability, observability and recoverability in real multi-agent systems.
