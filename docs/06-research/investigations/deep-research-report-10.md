# Supervisor–Implementer–Auditor System Architecture (Dopemux)

A **Supervisor–Implementer–Auditor** architecture cleanly separates orchestration, execution, and verification. We propose a central orchestrator (Supervisor) with dedicated worker agents (Implementers) and reviewer agents (Auditors), all coordinating via an explicit event bus and persistent store. The UI is tmux-based: each agent (Supervisor, Implementers, Auditors) runs in its own terminal pane with a stable ID, so users always know which agent is which【24†L169-L177】. Components include:

- **Supervisor (Orchestrator)** – Manages task workflow. It frames incoming requests into deterministic *task packets*, decides which Implementer(s) handle each packet, and enforces global constraints (budgets, stop criteria). It also invokes Auditors for post-checks. (This aligns with the “Conversation Coordinator” or “Orchestrator” role in multi-agent patterns【5†L262-L266】.) By centralizing control, the Supervisor ensures a consistent process, clear accountability, and a single point for logging and gating【39†L25-L28】.
- **Implementer Agents (Workers)** – Each implements a specialist, narrow task. On receiving a task packet, an Implementer invokes a CLI-based LLM (e.g. Claude Code CLI, OpenAI Codex CLI, Google Gemini CLI) or other tools (via MCP servers) to perform the work (e.g. writing code, running tests). Tool Agents encapsulate specific capabilities (code editing, Git operations, etc.) as callable services【5†L296-L301】. Implementers run independently (often in parallel) but only act on tasks assigned by the Supervisor.
- **Auditor Agents** – Validators that review Implementer outputs. After an Implementer finishes, an Auditor (which may itself be an LLM agent) checks correctness, consistency, and compliance. For example, one Auditor might be a “Critic” that uses a model to spot logical gaps, while another enforces schemas or tests (an Output Validator)【5†L318-L326】. Auditors enforce quality and safety (e.g. ensuring tests really verify the code) before results are accepted. Each audit step emits its own log.
- **Messaging & Event Bus** – An explicit, durable event system (e.g. message queue or publish/subscribe) carries all tasks and control messages. All communication is logged and sequenced. For instance, a **TaskCreated** event (with a unique ID and full context) is published when a new task is issued; **TaskStarted/Completed** events mark progress; **AuditRequested/Completed** events mark review steps. Using an event log (backed by a database) ensures **no hidden state** – every handoff is explicit and timestamped【36†L76-L80】.
- **Persistent State Store** – A durable database (e.g. SQLite or append-only ledger) records all task definitions, agent messages, and proof bundles. As in Agent Conductor, SQLite can store sessions, terminal IDs, messages, and approvals【24†L169-L177】. Every stage of a task writes to this store: the Supervisor records task packets and decisions, Implementers write their outputs and logs, and Auditors append verdicts. This yields a cryptographically auditable trail. For reproducibility, each task packet includes the random seeds, prompts, and tool versions used, so runs can be replayed exactly【22†L179-L181】【34†L85-L90】. (Much like deterministic debug replay, we package these as signed “proof bundles” for compliance【22†L179-L181】【19†L48-L56】.)
- **MCP Tool Integration** – All agents interact with external tools via the Model Context Protocol (MCP). Using MCP servers (Jenova, Jenova-powered clients, or custom MCP servers) standardizes tool calls, ensures permission management, and avoids hidden side-effects【13†L539-L544】. For example, Git, file I/O, or CI systems are exposed as MCP tools. This fits with multi-provider orchestration: agents use MCP for all non-LLM actions, guaranteeing consistent APIs and enabling an auditable chain of custody for tool interactions.

Each component has clear boundaries and responsibilities, avoiding any “free-for-all.”  Agents do *not* call each other directly; all handoffs go through the Supervisor and the event bus. Identifiers (e.g. task IDs, agent IDs) are stable and persisted, so routing is explicit, not implicit. This design meets the priorities of determinism, debuggability, auditability, and reproducibility: every decision is logged, every output can be traced back to inputs, and the entire run is fully replayable【19†L48-L56】【22†L179-L181】.

## 2. Agent Model

**Supervisor Agent**
- **Role:** Central coordinator. Receives high-level requests (from the user/UI) and decomposes them into ordered *task packets* with explicit parameters and success criteria【5†L262-L266】. Decides which Implementer agents to assign, in what sequence, and sets stop conditions or approval gates.
- **Inputs:** High-level task description; status updates/events from Implementers and Auditors. May consume workspace context (files, issue tracker state).
- **Outputs:** Task packets to Implementers; audit requests; final result or summary. Also writes to the event log.
- **Responsibilities:** Allocate work, manage context budgets, merge sub-results, enforce policies (budget, compliance). For example, it might plan: “Fetch latest code → run static analysis → implement feature X → run tests” and dispatch each step. It is analogous to a “planner/executor” or “supervisor” in agent patterns【5†L262-L266】【39†L1-L4】.
- **Failure Modes:** If the Supervisor itself hallucinates or mis-plans, the workflow breaks. To mitigate, it should validate each step’s preconditions (e.g. schema-check tasks) and retry or escalate on errors. It must not bottleneck the system, so implementers pull from a queue rather than block synchronously. Proper error reporting and the ability to re-send tasks (idempotently) are needed.

**Implementer Agents (Workers)**
- **Role:** Execute specific tasks as directed. Each runs as a terminal process (e.g. launching `claude-code`, `codex` CLI, `gemini-cli`, or similar). An implementer’s responsibility is narrow: given a task packet and its data, produce the required output (e.g. code change, analysis report) and return it to Supervisor. They act like “solvers” or “tool agents”【5†L290-L298】.
- **Inputs:** A fully specified task packet from Supervisor. This includes the working context (code files via MCP, prompts, constraints). Also receives any needed external data via MCP tools.
- **Outputs:** The raw result (e.g. modified code, test results, logs). They emit a **TaskCompleted** event (or error if failed) along with their output and logs. They update shared storage if needed (e.g. writing files via MCP).
- **Responsibilities:** Correctly invoke the underlying LLM or tool using the given prompt/context; handle retries if the call fails; log all interactions. They should run in a sandboxed environment (e.g. a dedicated git branch/worktree) to avoid conflicts. Each Implementer should be idempotent: if it crashes and the task is retried, it produces the same result or a clear failure.
- **Failure Modes:** Hallucinations or partially complete output. To address this, tasks should include verifiable success criteria (tests or schemas). If an Implementer fails (e.g. times out, error code), the system can retry or flag an error. Since tasks are deterministic packets, repeating an Implementer run should yield the same outcome (given fixed random seed and environment), aiding reproducibility【19†L48-L56】【34†L85-L90】.

**Auditor Agents**
- **Role:** Verify and review outputs. Each task passes through one or more auditors before final acceptance. Auditors check that the Implementer’s work meets quality requirements and did not bypass constraints. For instance, an Auditor might run the project’s test suite on the new code, or use an LLM “Critic” to validate logic.
- **Inputs:** The output from an Implementer (code changes, reports) and the original task packet. Also access to environment (tests, schemas).
- **Outputs:** An audit verdict and optionally annotated feedback. If the output is correct, the Auditor emits an **AuditCompleted** event (possibly marking the task as done); if issues are found, it can emit a **AuditFailed** event, possibly with a revised task (e.g. “fix the tests”). Audit logs and the proof bundle (input, output, rubric) are recorded.
- **Responsibilities:** Enforce formal correctness and policy rules. For example, a Validator agent checks JSON schema or required fields; a “Critic” agent might review natural language requirements for omissions. The auditor layer is like a QA gate, ensuring nothing silently fails.
- **Failure Modes:** False negatives/positives. To minimize this, audit criteria should be explicit (e.g. “no unauthorized file changes”, test coverage). Auditors should be deterministic (using fixed evaluation scripts) when possible. If an Auditor crashes, the Supervisor may treat it as a failed audit and trigger a manual review or retry in a different mode.

## 3. Execution Model

**Task Lifecycle:** A typical run proceeds as follows:

1. **Task Creation:** The user (in the tmux UI) issues a high-level request (e.g. “Implement feature X”). The Supervisor interprets this and publishes a `TaskCreated` event with a complete task packet (ID, context, instructions, success criteria).
2. **Task Dispatch:** Implementers subscribe to new tasks. A worker claiming the task emits `TaskStarted`. The Supervisor may also dispatch subtasks to multiple Implementers in parallel (fan-out) if applicable.
3. **Implementation:** Each Implementer processes the task: it loads the context (e.g. from an MCP Git server), calls the specified LLM or tool, and writes output. Upon finish, it emits a `TaskCompleted` event with its result (or `TaskFailed` if error). All inputs/outputs (prompt, random seeds, API calls) are logged.
4. **Orchestration Flow:** The Supervisor listens for completion events. Depending on the flow, it may sequence multiple steps (sequential orchestration) or aggregate parallel results. For sequential tasks, the Supervisor waits for one Implementer before sending the next subtask. For parallelizable work, it fan-outs and then optionally merges results. This flow is governed by explicit workflow logic in the Supervisor, not by the agents themselves.
5. **Auditing:** Once an Implementer’s output is ready, the Supervisor emits an `AuditRequested` event. An Auditor picks it up, reviews the output (running tests, checking schemas, or LLM-critique), and then emits `AuditCompleted` or `AuditFailed`. If failed, the Supervisor can retry the Implementer or break/stop the pipeline. Each audit step writes to the log with clear pass/fail status.
6. **Completion:** After successful audit, the Supervisor finalizes the task: it may merge code, report completion, or archive the result. A final `TaskDone` event is logged. The user can see a timestamped summary (as in VS Code’s orchestration: “a timestamped handoff report” is generated)【42†L1-L2】.

**Concurrency:** The system supports concurrent execution by running multiple Implementer agents in parallel. For example, different subtasks or independent tasks can be handled simultaneously. This uses a **fan-out/fan-in** pattern: Supervisor creates parallel branches, and later merges or evaluates them. Parallelism improves throughput (e.g. running analysis and coding tasks in parallel), but is carefully controlled to avoid conflicting changes. Implementers lock or isolate shared resources (e.g. using separate branches or worktrees).

**Orchestration Flow:** We use a hybrid orchestration pattern. Control decisions reside with the Supervisor (centralized decision-making) for predictability【39†L25-L28】, but execution is decentralized among Implementers. All sequencing is deterministic – the Supervisor’s workflow explicitly defines the order or parallel groups. There are checkpoints (e.g. after each stage or before major changes) where state is persisted, so failures can be retried without replaying earlier work. This ensures determinism: given the same inputs and seeds, replaying the event log yields the same outcome【19†L48-L56】【34†L85-L90】.

## 4. State Management

- **Persistent Store:** A central database records all task-related state and logs. We use it to store (a) *task definitions* (full packets with IDs and parameters), (b) *agent messages/events*, and (c) *proof bundles* (snapshots of I/O for each task). For example, Agent Conductor uses SQLite to persist sessions, terminals, and inbox messages【24†L169-L177】. Similarly, every event (creation, start, complete, audit, etc.) is written as an immutable log entry. This persistent log is the core of auditability【22†L179-L181】.
- **Ephemeral vs Persistent:** Agents themselves hold minimal ephemeral state (current task context). They do not keep hidden global state between tasks – all important data flows through events or via MCP servers. For instance, an Implementer loads files from a Git MCP server on demand rather than caching them invisibly. Any needed “memory” (like summaries of past runs) is managed explicitly by a Memory Manager component. According to multi-agent patterns, a Memory Manager can store long-term facts or summaries【5†L337-L345】; we would use it for project knowledge or user preferences, ensuring continuity without polluting agent contexts.
- **Memory Boundaries:** Each agent process has its own private memory (stack, variables) that resets per task. No agent reads another’s memory. Cross-agent data sharing is only via the event store or through services. For example, the Supervisor might pass a context ID to an Implementer, which then fetches details from the database or an MCP cache. This avoids hidden caches and makes state flows explicit.

## 5. Event System

**Event Types:** We define a clear set of event types (illustrative list):

- `TaskCreated` – Supervisor emits when a new task packet is ready.
- `TaskAssigned` – Supervisor or system signals an Implementer to start.
- `TaskStarted` – Implementer acknowledges it has begun a task.
- `TaskCompleted` – Implementer emits on successful completion (with output).
- `TaskFailed` – Implementer emits on failure (with error details).
- `AuditRequested` – Supervisor signals an Auditor to check a result.
- `AuditCompleted` – Auditor signals pass (with any comments).
- `AuditFailed` – Auditor signals failure (with feedback).
- `TaskDone` – Supervisor finalizes the task after successful audit.
- (Other meta-events: e.g. `AgentRegistered`, `ResourceUpdate`, etc.)

**Event Flows:** The Supervisor drives the flow by emitting events and reacting to them. For example, on `TaskCompleted`, it checks success criteria and then issues `AuditRequested`. Events flow through a durable queue or message broker. Agents subscribe to relevant event types and filter by task ID or role. Because all events are recorded, we have a full timeline of the workflow.

**Idempotency:** Each task has a unique ID; event handlers ensure idempotency. For example, if an Implementer crashes after emitting `TaskStarted` but before output, it can safely re-run the task (the Supervisor sees no `TaskCompleted` and can reassign). We use an idempotency key (often the task ID) so that duplicate events (e.g. two `TaskCompleted` for the same task) are ignored or merged. Checkpointing (persisting outputs at each stage) ensures that replaying events produces the same state. As the trust article notes, treating LLM calls as near-deterministic and logging everything enables reliable replay verification【34†L85-L90】【22†L179-L181】.

## 6. Tradeoffs

- **Centralized vs Distributed Orchestration:** A centralized Supervisor simplifies consistency and audit: “central control tends to produce consistent user experience and clear accountability”【39†L1-L4】. It’s also easier to enforce system-wide constraints (deadlines, budgets) and to log a single narrative【39†L25-L28】. A fully decentralized (peer-to-peer) model would add flexibility but complicate routing and coordination【39†L7-L10】. Given our priorities, a *hybrid* is best: one central Supervisor for decision-making, but with multiple worker processes for parallelism. This matches the common “manager–worker” pattern【39†L1-L4】【39†L25-L28】.
- **Synchronous vs Asynchronous Agents:** Synchronous (strict sequential calls) is easier to reason about but can underutilize resources. Asynchronous agents (event-driven, parallel) improve throughput and resilience. We opt for asynchronous execution with well-defined sync points (checkpoints). For instance, Supervisor waits for all Implementers to finish stage 1 before moving to stage 2 (a synchronous step), but within each stage, multiple Implementers run concurrently. Explicit event barriers make the system deterministic while still benefiting from concurrency.
- **Single vs Multi-Implementer:** A single implementer (one agent doing all work) simplifies state and is inherently reproducible, but is a throughput bottleneck. Multiple Implementers allow parallel task handling and specialization (e.g. one agent for frontend code, another for backend). The tradeoff is complexity: multiple agents require explicit coordination and merging of results. We mitigate this by having the Supervisor orchestrate splits/joins and by using our event/log system to unify outputs. Costs can also guide this decision: high-cost models could be invoked concurrently to save time. With our model router (see below), tasks can be farmed out to cheaper models in parallel, making multi-implementer more efficient on both speed and budget.

## 7. Recommended Design

Our final architecture combines these elements into a robust, production-grade system:

- A **Supervisor service** (e.g. a FastAPI server) runs continuously and manages tasks. It launches a tmux session with sub-windows (agents). Each window sets a unique `CONDUCTOR_TERMINAL_ID` environment variable【24†L169-L177】 so the Supervisor always knows which pane is which.
- Agents (Implementers and Auditors) are **pluggable adapters**. Each adapter knows how to run a specific CLI (Claude Code, Codex, etc.) by feeding keystrokes or invoking APIs【24†L177-L179】. For example, a “claude_code” worker opens a tmux pane and runs `claude-code` under the hood. Additional adapters (e.g. a “tester” agent) can run scripts or call LLMs as needed. Each agent process has no hidden global memory; it only reads the task packet from the Supervisor and writes results back.
- **Determinism and Auditability:** Every step logs its full context. Inputs (prompts, files) and outputs (code changes, LLM responses) are captured. We attach a cryptographic hash (or signature) to each proof bundle to prevent tampering【22†L179-L181】. The event store effectively becomes an immutable ledger【22†L179-L181】. In practice, this means if a developer questions a result, we can replay the exact sequence: “See Task #42 had prompt X and model Y with seed Z, Auditor confirmed condition C.” This matches the vision of *verifiable agentic AI*, where replay logs form the compliance record【34†L85-L90】【19†L48-L56】.
- **Multi-Provider Routing:** A key component is an **LLM Model Router** sitting between Implementers and providers. When an Implementer needs an LLM call, it actually queries the router with the task’s complexity and budget context. The router then selects a model (e.g. send a simple query to a small LLM, send a complex subtask to GPT-5 or Claude Opus), as suggested by industry best practice【45†L95-L100】. This enforces cost constraints: “the router can enforce budget limits and select cost-effective models”【45†L95-L100】. It also handles failover (if one provider is down) and consistent API formatting. This way, we avoid overpaying (e.g. no need to always use the largest model) while ensuring quality. Cost and latency policies are encoded in the router (e.g. if budget is low, route to cheaper LLM).
- **Event Logging & UI:** Every task transition produces a timestamped report. For transparency, the tmux UI shows the Supervisor log and an agent dashboard. The Supervisor prints a summary of each handoff (“Supervisor dispatched Task #42 to agent ‘coder’; received completion at 12:34:56, then began audit”) and time-stamps it【42†L1-L2】. Users can scroll back or query logs to trace exactly what happened when.
- **Memory and Context:** We incorporate a Memory Manager component (per [5]) that persists useful context (e.g. “Feature X specification from last week”). Agents consult it via MCP so that they don’t have to re-learn facts. However, even this memory is versioned and snapshot in the log, so long-term drift is tracked.

In summary, our design is a **centralized, event-driven** architecture with clear role separation. It avoids the pitfalls of “agent free-for-all” by using fixed IDs and queues【24†L169-L177】. It avoids hidden state by making the event store the ground truth. It avoids implicit routing by delegating all task assignments to the Supervisor/router. At the same time, it leverages **parallel implementers** and **multi-model routing** to meet performance and cost goals【45†L95-L100】. Critically, by building in deterministic task definitions and comprehensive logs, the system ensures that every output is reproducible and auditable【19†L48-L56】【22†L179-L181】. This balance of central control and flexible execution, with explicit checkpoints and signed proofs, best meets the priorities of Dopemux: a debuggable, traceable, reproducible multi-agent system that scales across providers without sacrificing trustworthiness.
